# 对话式 AI 员工工作空间：任务到交付的审核流程

状态：实现依据（2026-10-27）

## 要解决的问题

当前工作空间会把目标直接交给员工执行，展示任务清单与百分比，但用户缺少一份清楚的计划、执行证据和交付验收入口。生成的网页、后端和测试报告可能彼此未接通；不能只因文件存在就表示完整应用已经可用。

## 参考与取舍

GitHub Copilot cloud agent 的流程包含：提出任务、研究与计划、执行并查看会话记录、审阅差异与验证结果、由人决定是否接受或要求修改。参考：[计划与迭代](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/research-plan-iterate)、[会话监控](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)、[结果审阅](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/review-copilot-output)。

本产品面向普通用户，第一阶段采用**工作空间内的交付审核**：任务继续自动启动，避免每次都卡在计划审批；并行新增任务保留人工审核。生成结果完成后才出现“接受交付／要求修改”。这里的交付审核不是 GitHub PR，也不宣称测试已运行。

## 用户流程

1. 用户提出目标，主管生成可读计划：目标、分工、依赖、验收要点。工作立即开始。
2. 任务卡显示清单百分比、各员工在做什么、最近动作。用户可补充要求；补充内容用于尚未开始的步骤，运行中的步骤不会被暗中改写。
3. 主管推荐能并行进行的额外工作，只有人工审核同意后才会分配。
4. 工作结束后生成交付包：文件入口、静态检查结果、尚未运行的检查、已知限制。状态为“待你验收”。
5. 用户“接受交付”后记录决定；“要求修改”需填写具体意见，系统据此建立关联的新任务，旧交付及审核记录保留。

## 关键状态和约束

- `run.status` 仍负责执行生命周期：`pending/running/completed/failed/cancelled`。
- `run.review.status` 单独负责交付决定：`pending/accepted/changes_requested`；仅完成的任务可审核。历史完成任务没有 `review` 时视作 `pending`。
- 新任务有 `run.plan`，包含目标说明和用户可核对的验收要点。旧任务按原数据展示。
- 修改意见创建 `followupRunId`，新任务的 `sourceRunId` 指回原任务；二次审核不能重复创建后续任务。
- 修改任务使用当前已连接的模型；上一次通过 `/` 临时调用的 Skill 不会自动带入新任务。
- 修改任务会读取原任务的完整文件产物，总量上限 80 KiB；超出时拒绝建立任务并请用户精简文件，不会悄悄截断旧代码。
- 运行中补充要求只进入对应 run 的后续步骤，不泄漏给同 Session 的其他 run。
- 执行证据只记录系统实际做过的检查。HTML 结构、脚本存在、JavaScript 语法可做静态检查；浏览器实际操作和端到端测试未运行时必须明示。
- 会话与文件继续按 Session 隔离；审核和补充要求也必须验证 Session 所属关系。
- 查询、取消和重试 run 也使用带 Session ID 的 API，并核对归属。
- 本阶段不接 GitHub 仓库，不创建真实 PR，不自动部署生成代码。后续可将同一交付包映射到 GitHub PR。

## 界面

对话仍是主界面。每次任务卡依次展示：目标与计划、清单和进度、团队小日报、最近动作、交付包与审核。普通用户看到“页面结构已检查／实际运行未验证”等证据；开发者模式仍可看原始事件。审核决定清楚显示时间和意见。

## 验收场景

- 新的 Web 任务一提交就可见分工与验收要点，工作继续执行。
- 运行中补充要求会保存在当前会话，并出现在后续尚未启动步骤的上下文中。
- 完成后，HTML 与后端文件的静态证据、未运行的验证和可点击产物均可见。
- 接受交付和要求修改只能二选一；要求修改生成关联任务，原文件与审核历史仍在。
- 另一个 Session 无法审核或修改本 Session 的任务。
